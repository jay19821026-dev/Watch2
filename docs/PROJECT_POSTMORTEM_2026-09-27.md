# September Project Review — 2026-09-27

## Executive finding

The project has not been stuck because every sensor has one independent defect. Work repeatedly expanded across sensor access, derived health algorithms, UI, AI, battery, debug tooling, and device validation without one frozen acceptance target. Changes then crossed producer, storage, calculation, export, and UI boundaries without a mandatory contract-level regression test. That made “fix A, break B” likely and made green builds look more conclusive than they were.

## Evidence from the month

- The project log records many successful builds, installs, sensor scans, and UI fixes, but repeatedly says a fresh paired-device scan or visible post-install verification was still pending. Build success was often reported beside hardware uncertainty, and older records became inconsistent with the latest tracker.
- Sensor outcomes were frequently collapsed in discussion: no event, stale cached row, rejected signal, uncalibrated raw packet, OEM/manual-mode restriction, and hidden UI are different failures. The code’s staged pipeline is the right organizing model; acceptance evidence did not consistently follow it end to end.
- Sample counts had overloaded meanings across the watch/phone boundary: finite biomedical values, callback events, and down-sampled display points. The phone could then use a display-compatible count as a physiological sample-count gate or label received events as absent.
- The working directory has no Git metadata. Consequently, historical attribution, reliable diff review, and rollback-by-commit are unavailable; project notes also show version/status drift. This is a process and recovery risk, not proof that an individual code change caused every reported regression.
- External AI agents were useful as adversarial reviewers, not shared-workspace engineers. They could not inspect the repo directly; summaries and guessed source paths led to contradictory advice. Only a small, explicit source excerpt was needed for the latest Claude review. AI agreement is not test evidence.
- Independent review by six task agents converged on the same process failure chain: scope/WIP expansion → cross-layer contract changes → incomplete producer-to-consumer tests → builds mistaken for device acceptance. Reviewers also cautioned against indiscriminate edits: Wear biomedical `samples` is finite extracted values, while `event_count` and retained preview points are separate; its count-threshold uses are not automatically bugs. Their findings are advisory and were checked against current source.

## Current concrete defect found and corrected

The current count contract separates raw biomedical count from event count, preview length, and legacy display compatibility. Review of the exact source found an additional bug: a missing `raw_value_count` in a v2 packet was defaulted to integer zero before parsing, making “unknown” indistinguishable from an explicit zero. This is corrected by preserving field absence as `null`. Presence/freshness now uses a separate event/raw/preview predicate; biomedical statistics and HRV gating use finite raw counts only. Non-biomedical channels retain their own reported-sample path.

Affected areas include `RawSensorPayloadPolicy`, `WearDataProcessor`, Health Center/export freshness, raw sensor detail verdicts, Clinical Lab, measurement-result displays, and received-vs-quality-rejected feedback. Tests cover explicit zero versus missing v2 counts, legacy display fallback, received events with zero finite values, and the separate non-biomedical path.

Claude’s excerpt-based review found the nullable defect above. Its concern that non-biomedical counts would be zeroed was not supported by the actual branch: those channels bypass the biomedical raw-count resolver and use their reported `samples`. The implementation now makes this branch explicit and tests it. Claude did not inspect the whole repository; Codex performed the consumer search and local validation.

The six-agent review found one additional, concrete presentation defect: the phone result page rendered unavailable legacy/v2-missing raw and event counts as numeric zero. A follow-up review also found missing preview/non-biomedical counts used the same zero default. These are now corrected: absent counts render as unknown, explicit zero remains zero, and the receiver marks event-count availability from actual field presence rather than contract version alone. Added focused tests cover unknown versus explicit zero. This is a display/metadata correction, not a sensor-acquisition fix.

## Additional cross-surface findings

- A consumer-side audit found a reproducible producer inconsistency: `RawVitalsProbe.derived(emptyList())` reported `samples=1` and `channels=1` despite zero values/events. It is now zero for empty input; a Wear regression test covers the empty case. This explains a class of misleading “has a sample” metadata, but does not prove it caused a specific historical scan failure.
- Wear Data Layer final-snapshot writes currently log enqueue failure but have no durable retry. On phone, raw snapshot persistence uses `SharedPreferences.apply()` and asynchronously deletes the DataItem; process death between those operations is a possible loss window, not a failure observed in the recorded exports. A safe fix needs idempotent receive + durable commit-before-delete and fault-injection tests; blindly retrying with new paths risks duplicate snapshots.
- Both `release` Gradle variants are explicitly signed with the debug signing config. This is verified in source and blocks calling these APKs production-release artifacts. Production signing requires a separately provisioned secure keystore/CI secret; none should be added to the repository.
- ADB is present in the workspace, but currently reports no connected devices. Earlier wording that the executable was unavailable was inaccurate.
- Independent algorithm review also verified that waveform quality returns invalid when the sampling rate is non-positive; the regression test explicitly asserts unknown-rate input cannot produce RR intervals. This is an algorithm safety guard, not a new device result.
- Reviewers proposed that 38 same-time duplicate rejects might mean unique samples were lost. Source inspection does not establish that: `RawSnapshotOrdering` accepts equal timestamps except for a preview arriving after a final snapshot, while HR has a separate feature-ordering gate. The old counter labels also explicitly say duplicate delivery/timestamp collision is not unique measurement loss. Need correlate event identity and rejection reason before changing dedupe.
- Claude independently flagged that a future naive DataClient retry could mint a new UUID path per attempt. Source confirms paths are created at publish time and there is no durable retry queue; however, this is a recovery/idempotency risk, not proof of historical loss. Do not add unbounded retry. Phone receive currently asynchronously deletes DataItems after `SharedPreferences.apply()`; commit-before-delete with dedupe and a failure-injection test is the safer next transport fix.
- Several external AI suggestions were rejected as overconfident: missing/zero sensor timestamps do not prove uninitialized HAL memory; Doze plus no notification does not prove the app was killed; callback receipt time must not substitute for source time; a universal 5-second timeout and a `max(samples, preview)` rule are not supported by current contract or evidence.

## Root causes and corrective operating rules

1. **Scope/WIP overload:** freeze new feature work until one end-to-end data-integrity goal closes.
2. **Contract drift:** any wire semantic change must update producer, consumer, formula gates, freshness/status, export, and tests in the same change. Keep unknown, zero, event count, raw count, and preview count distinct.
3. **Weak release evidence:** unit tests/builds prove code consistency, not watch acquisition. Require a new UI-started paired session with one correlated session ID and explicit per-channel outcomes before calling a device issue fixed.
4. **No source history:** establish Git or another immutable patch archive before the next broad refactor; record build/version, tests, changed paths, and install/scan evidence together.
5. **AI process:** assign each reviewer one bounded question and provide only the minimal sanitized evidence; Codex reconciles advice against actual source and tests. Do not wait for unanimous agreement or treat a response as execution.

## One closure objective

Complete a producer-to-phone regression for the versioned count contract, then perform one fresh paired-device scan and reconcile acquisition → payload/units → quality/calibration → watch snapshot → Data Layer → phone storage → freshness → UI. No new sensor, AI diagnosis, or health algorithm work until that objective passes or every failure is assigned to a specific boundary with evidence.

## Review council follow-up — persistence and algorithm risks — 2026-09-27

- Six internal reviewers were assigned PM, pipeline, persistence, sensor algorithms, release QA, and clinical-safety roles; Claude independently reviewed the narrow Android persistence question. Their shared process recommendation is to freeze scope and close one evidence-backed acceptance gate before adding features.
- **Fixed in this pass:** if phone `SharedPreferences.Editor.commit()` returns false, receipt and snapshot changes may still be visible in the process cache before durable storage is confirmed. A redelivery could therefore mistake the in-memory receipt for durable storage and delete the Wear DataItem. The receiver now tracks failed receipts by channel; it retries ordering bypass only when the same failed URI is still the channel's latest in-memory snapshot. If a newer snapshot superseded it, the receiver first flushes the current preference state and retains the DataItem if that flush fails. Successful commit clears pending receipt state for that channel. Focused retry-state test, full mobile/Wear unit tests, and both Release assemblies pass.
- **Not proven by tests/device:** retry-state tests exercise decision policy, not a failing Android `SharedPreferences` disk write; no paired-device/Data Layer failure-injection run was available. The Android contract says changes may be reflected in memory before durable persistence; see [SharedPreferences API](https://developer.android.com/reference/android/content/SharedPreferences).
- **Algorithm issues found; not silently changed in this transport patch:** raw vendor temperature is accepted as °C solely because it falls in 20–45; sleep session duration is used as sleep duration and HR-inferred sleep can enter scores; ECG RR output depends on a timebase mapping not established by the available device evidence; ECG/BioZ quality scores can be raised by RR count or waveform length. These need separate unit/source-aware patches and explicit tests, not threshold tuning.
- **Other unresolved delivery risk:** Wear final Data Layer publish failure is log-only; there is no durable outbox/retry. Any future outbox must persist the exact logical capture identity and reuse its DataItem path on retry. Historical scans do not prove this caused their missing channels.
- **Release gate remains closed:** no connected devices were available in this pass; current Release variants use the Android Debug certificate, and the reviewer found same-version `dist/` APK hashes differ from the just-built artifacts. Do not install/publish or call the build a device acceptance until one hash-pinned pair and a fresh paired scan are verified.
