# Data-window audit / 資料時間窗對照

## 9.8.348i vs 3.59.2i / 兩版交叉核對

The local 9.8.348i decompilation exposes `com/xiaomi/fit/fitness/export/data/item/HrItem.java` (`time`, `bpm`) and `Spo2Item.java` (`time`, typed SpO2), plus `com/xiaomi/fitness/repo/heartrate/HeartRateBiz.java`, `spo2/Spo2Biz.java`, `sleep/SleepBiz.java`, and `teperature/TemperatureBiz.java`. The 3.59.2i decompilation exposes the separate Health Connect writer path under `com/xiaomi/fitness/repo/healthconnect/biz/daily`. These are two inspected APKs and two different paths; the 9.8.348i aggregation code must not be described as a Health Connect writer.

本機 9.8.348i 反組譯可核對原廠型別化資料項目與彙總類別；3.59.2i 則另有 Health Connect 寫入路徑。兩個版本、兩條路徑不可混稱。

| Metric / 項目 | 9.8.348i typed aggregation / 型別化彙總 | 3.59.2i Health Connect export / 寫入 | AILISA status / 狀態 |
| --- | --- | --- | --- |
| Heart rate / 心率 | `HeartRateBiz` keeps positive `HrItem.hr`, uses each `HrItem.time`, and groups by view tag into minute, half-hour, hour or day buckets. | `HrSyncBiz` puts sample timestamps into `HeartRateRecord`; the enclosing record uses a separate sync bucket. | Reads individual sample timestamps and bpm. The detail page now filters samples to `[start, end)` **before** validating them, so a boundary-spanning OEM record does not invalidate the whole page. OEM display aggregation and source priority are not reproduced. / 逐筆時間與數值對應；圖表彙總不等同原廠。 |
| Oxygen / 血氧 | `Spo2Biz` keeps positive typed `Spo2Item.spo2`, uses `Spo2Item.time`, and groups chart values by hour, half-hour or day. | `Spo2SyncBiz` writes typed SpO2 to `OxygenSaturationRecord.percentage` at `Spo2Item.time`. | Reads typed Health Connect percentage and measurement time. ### Heart-rate and oxygen chart buckets / 心率與血氧圖表分桶

Both inspected versions' `HeartRateBiz.splitDailyReport` and `Spo2Biz.splitDailyReport` use half-hour buckets for `days` and day buckets for `weeks`/`months`. In each chart bucket they write an integer array of **distinct values**, not one average. `Spo2Biz` also calculates a separate daily integer mean, min, max and count below 90 from typed positive `Spo2Item` values. The 3.59.2i `Spo2Biz` has additional source-ID grouping after the inspected latest-record calculation; the 9.8.348i excerpt does not establish identical downstream report contents. These are display/report transformations, not evidence of sensor calibration or a diagnostic rule. / 兩版日圖均以半小時、週／月圖以天分桶；每桶保留不重複整數值陣列，並非單一平均。3.59.2i 另有後續來源 ID 整理，不能直接宣稱兩版報表完全相同。

AILISA's seven-day descriptive Health Connect SpO₂ summary now excludes zero as a missing/invalid value before calculating min, max, sample count and the below-90 percentage, matching the inspected OEM daily-report positive-value gate. Its input is still Health Connect, not the OEM typed result store; this change does not import the OEM measurement or prove clinical validity. / AILISA 的七日描述性摘要先排除 0，再計算範圍與低於 90% 的樣本比例；輸入仍是 Health Connect，不能視為移植原廠量測演算法。

AILISA's phone detail chart previously drew heart rate in fixed five-minute/hour/day/week UTC-second buckets and oxygen as individual dots. It now uses **local half-hour** buckets for day and **local-day** buckets for week/month, with a local-month bucket for AILISA's extra year view. It draws the minimum-to-maximum range (or one dot for a single value) from the selected Health Connect source. Its overview statistics and raw rows remain based on individual Health Connect values; they do not implement the OEM distinct-value arrays, source grouping or integer daily mean. / AILISA 詳細頁已改成本地半小時／天／月的圖表粒度，以選定來源的最低至最高值畫線；統計與原始列仍取自 Health Connect 單筆值，不冒充原廠去重陣列或日均值。

Decompiled Java can misrepresent Kotlin boundaries; the statements here are limited to visible call paths. This audit does **not** establish the OEM's clinical decision window or signal calibration.

本頁對照 2026-11-08 本機反組譯的 Mi Fitness 3.59.2i。所列路徑是研究用本機素材，不隨 AILISA 發行。反組譯 Java 對 Kotlin 邊界可能失真；下表只記載能核對的呼叫路徑，**不能**據此宣稱掌握原廠臨床判讀窗或訊號校準。

## Watch ECG event path / 手錶 ECG 事件路徑

Decompiled `XiaomiHealth-watch-decompiled/sources/we/b.java` (`EcgSensorUtil`) registers sensor type `65573` and on-body sensor type `34`. Its callback skips the first 20 ECG events, then requires field 10 to equal `1000` and an on-body state before sending the first ten event fields to `EcgJni.algInputSignal`. It negates those ten fields when `Settings.Global.wear_wrist_orientation_mode` is `2` or `3`; other modes keep the sign. It starts from `event.timestamp` in milliseconds and increments two milliseconds for each of the ten fields. These are **observed OEM program decisions**, not an independently verified HAL sample clock, electrode mapping, ADC scale, or clinical calibration. The JNI implementation and its validation data are not established by this Java decompilation.

AILISA mirrors the observed warmup, marker, on-body check, and wrist-orientation sign **only in its labeled OEM-conditioned preview**. The raw first-field event trend remains available even when those conditions fail; it is labeled as an unqualified raw value, not an ECG result. Original event rows remain unchanged. AILISA does not synthesize 2 ms sample timestamps for analysis from this observation, because the device's actual sampling clock has not been verified. Without that clock and a validated amplitude scale, the raw values do not support an ECG heart rate, RR interval, rhythm classification, or mV report.

原廠解包的 `we/b.java` 可確認：感測器 `65573` 的前 20 個事件略過；第 11 欄為 `1000` 且離腕感測器 `34` 回報配戴時，將前 10 欄送進 `EcgJni.algInputSignal`。`wear_wrist_orientation_mode` 為 `2` 或 `3` 時先反轉數值符號；原廠程式由事件時間戳開始，每欄遞增 2 毫秒。這是原廠程式**怎麼使用數值**的證據，並不等於已驗證手錶 ADC 取樣時鐘、電極映射或 mV 校準。AILISA 對齊可確認的預覽條件，同時允許查看未通過條件的原始第 1 欄趨勢；兩者分開標示，原始資料保持不變。

The OEM result screen in `XiaomiHealth-watch-decompiled/sources/com/xiaomi/wear/fitness/health/ecg/EcgResultActivity.java` maps native `getAnalysisResults()` codes `200` to sinus rhythm, `201` to atrial fibrillation, `202` to low heart rate, `203` to high heart rate, and `204` to uncertain. `EcgJni.java` loads the proprietary `fitness` native library; the Java decompilation exposes `algInputSignal`, `getAnalysisResults`, and `getAverageHr`, but not their algorithms or calibration/validation parameters. These result codes are **outputs of the OEM native pipeline**, not labels that can be assigned to AILISA's raw HAL values by comparing thresholds. AILISA must obtain a valid OEM result through a supported export or independently validate its own classifier against paired Watch 2 Pro recordings and clinical reference before reporting a diagnosis.

原廠結果頁可見代碼 `200` 竇性心律、`201` 心房顫動、`202` 心率偏低、`203` 心率偏高、`204` 無法判定；代碼來自原廠 `fitness` 原生函式庫的判讀結果。解包 Java 只能看見介面及結果映射，不能證明 AILISA 已有相同演算法或準確率，也不能把原始數值直接套上這些診斷標籤。

## PPG channels / PPG 通道

The decompiled watch `MiHealthService-decompiled/sources/com/xiaomi/wear/fitness/whs_service/collection/DataCollectionService.java` distinguishes sensor `65597` as a heart-rate optical raw stream (`ppgHr`) and `65596` as a blood-oxygen optical raw stream (`ppgSpo2`). Its CSV headers have different red/IR/green field layouts depending on collection mode. This class is a raw-data collection/export path; it does not prove that the raw fields are calibrated heart rate or SpO₂ percentages, nor does it expose a disease classifier. AILISA must keep these channels separate and use a typed OEM/Wear Health Services result when displaying a measured physiological value. A PPG waveform may support a research pulse estimate when its sampling clock and signal quality are adequate, but it cannot by itself establish a disease diagnosis.

原廠 `DataCollectionService.java` 將 `65597` 作為心率光學原始通道、`65596` 作為血氧光學原始通道，輸出欄位依收集模式不同。這段解包程式是原始資料收集與匯出路徑，沒有證明原始欄位已換算成心率／血氧百分比，也沒有疾病分類器。AILISA 會分開保存與標示這兩個通道；有可靠時基及品質證據時，PPG 可提供研究用脈搏估計，但不能僅憑波形宣稱疾病診斷。

The phone home summary now applies the same overlap-and-clip rule to sleep-session fallback totals. Its label says *recorded interval*, because the OEM `SleepSyncBiz` uses bed/wake timestamps and stage records separately; the interval sum is not verified actual sleep. / 手機首頁的睡眠備援總時長也改為保留交集、按查詢界線裁切，並標明是紀錄區間，不能當作原廠實睡時長。

Mi Fitness's `Spo2SyncBiz.java` writes each `Spo2Item.time` as the `OxygenSaturationRecord.time` and its typed `spo2` value as `percentage`; the metadata modification time is separate. AILISA's phone home now checks this measurement time against its local seven-date query before selecting the newest oxygen record. The typed percentage remains separate from raw optical `65596` events. / 原廠逐筆血氧使用 `Spo2Item.time` 作量測時間、`spo2` 作百分比；AILISA 首頁先按該量測時間篩選，再挑最新紀錄，不將光學原始事件轉成百分比。

Mi Fitness's `repo/teperature/TemperatureBiz.java` aggregates typed `TemperatureItem` entries by their `time` for a daily report. The inspected `repo/healthconnect/biz/daily` package contains no temperature writer analogous to `Spo2SyncBiz`; this is a bounded source observation, not proof that Mi Fitness never exports temperature elsewhere. AILISA therefore labels a Health Connect temperature record by its actual data origin and does not present raw Watch 2 Pro sensor fields as the OEM daily temperature report. / 原廠溫度日報表依 `TemperatureItem.time` 整理；已檢查的 Health Connect 同步目錄未見對應寫入類別，不能據此宣稱原廠從不匯出。AILISA 的 Health Connect 溫度須標來源，手錶原始值不冒充原廠日報表。

The decompiled `TemperatureBiz.computeSummaryData` also keeps `TemperatureItem.bodyTemp` and `TemperatureItem.skinTemp` in separate summary fields, with separate positive-value checks. AILISA currently reads `BodyTemperatureRecord` with wrist measurement location from Health Connect. Its seven-date deviation is an AILISA descriptive median, not the OEM skin-temperature report or its averaging algorithm. The UI now names this source and distinction explicitly. / 反組譯的溫度日報表分別處理 `bodyTemp` 與 `skinTemp`；AILISA 讀的是 Health Connect 腕部位置的 `BodyTemperatureRecord`，其個人中位數差異不是原廠皮膚溫度日報表或原廠平均演算法，畫面已明確標示。

For OEM temperature charts, `TemperatureBiz.computeTimeDiffValueRecords` calls `BaseProcessBiz.groupByHour` for `home`, `groupByHalfHour` for `days`, and `groupByDay` for `weeks` and `months`. These are chart buckets for typed OEM temperature items, not calibration or a diagnostic window. AILISA's Health Connect detail limits the wrist-temperature chart to wrist-location records and withholds a core-temperature reference score. / 原廠溫度圖表在 `home` 以小時、`days` 以半小時、`weeks`／`months` 以天分桶。這是原廠型別化溫度項目的圖表分桶，並非校準或診斷窗口。AILISA 的 Health Connect 詳細頁只保留腕部位置紀錄，不以核心體溫範圍評分。

AILISA's wrist-temperature detail chart now uses the matching **time granularity** where its view maps to an OEM view: day = local half-hour, week/month = local day. Its extra year view uses local month buckets. Each AILISA chart point is the arithmetic mean of Health Connect records from one selected origin in that bucket; the latest value and raw rows remain individual records. OEM `TemperatureBiz` instead groups its own typed `TemperatureItem` values and removes duplicate primary/secondary values within a bucket. Thus matching granularity does not make the values or aggregation equivalent. / AILISA 腕部體溫圖表在日頁採當地半小時、週／月頁採當地日期，額外的年頁採當地月份；同一來源每桶以 Health Connect 紀錄算術平均顯示，最新值仍是單筆。原廠則使用自己的型別化溫度項目，且會在桶內去除重複的主／次值，因此粒度相同不代表數值或聚合方式相同。
