# Clinical Data and Product Gate — 2026-09-28

## Decision

Build a governed research-data and validation pipeline first. Do not train a diagnosis model or market the current Xiaomi Watch 2 Pro integration as clinically equivalent to a medical device. Public medical databases can support algorithm research and software tests; they cannot supply this watch's sensor transfer function, OEM calibration, or device-specific clinical validity.

Separate three data stores and purposes:

1. **Public research corpus:** dataset metadata, permitted derived features/labels, license and citation, reproducible splits, and evaluation outputs. Keep source files in an approved research workspace; do not embed licensed waveform corpora in the consumer APK.
2. **Consented paired-validation cohort:** only after protocol, ethics/privacy review, consent, reference-device protocol, and secure access controls. Pair watch output with a traceable reference measurement and clinical labels where applicable. User authorization alone is not a substitute for any required ethics, privacy, or regulatory process.
3. **Consumer health records:** user-controlled Health Connect/watch records, isolated from research training by default. No silent/background upload or cross-user pooling.

Before importing any data, create a dataset registry with version/DOI, owner, acquisition protocol, sensor and units, annotation provenance, population, inclusion/exclusion criteria, access level, license/DUA, commercial-use status, retention/deletion, citation, and checksum. Do not scrape or redistribute datasets outside their terms.

Do not treat repository-wide defaults as dataset-specific permissions. For example, the MIMIC-IV data are credentialed and DUA-restricted; WESAD is described by its maintainers as non-commercial; CC BY datasets still require attribution and license review. A restricted research dataset must not be sent to unapproved external AI services. Dataset suitability, model transferability, and commercial permission are separate decisions.

## Minimum data model for paired validation

Each record needs pseudonymous participant/session IDs; consent/protocol version; watch model/firmware/app build; sensor channel and raw-vs-derived designation; timestamp and clock source; sampling rate or explicit `unknown`; units or explicit `unknown`; contact/motion/charging context; quality flags; reference device/model/calibration/date; reference value and uncertainty; annotation source/reader/adjudication; missingness and exclusion reason; processing/model version; and immutable provenance/audit events. Keep direct identifiers and linkage keys in a separate restricted store. Encrypt in transit/at rest, least-privilege access, retention expiry, export audit, and deletion workflow are prerequisites.

Use established semantics rather than inventing a proprietary data contract: FHIR `Observation` for measurements, `Device` for device context, `Provenance` for transformations, `Consent` for permitted use, and `AuditEvent` for access/export records. These are interoperability patterns, not a substitute for consent enforcement, security engineering, or jurisdiction-specific review.

## Evidence gates before a clinical claim

1. **Acquisition:** demonstrate repeatable capture on this exact hardware and software build; quantify missingness, dropout, motion/contact effects, and operating conditions.
2. **Analytical validity:** compare the algorithm output with a traceable reference under a prespecified protocol; freeze units, clocks, tolerances, and acceptance metrics before testing.
3. **Clinical association/validation:** define intended use, population, comparator, endpoint, sample-size rationale, subgroup analysis, independent external validation, and prospective protocol with qualified clinical/statistical oversight.
4. **Safety and lifecycle:** risk controls, usability, cybersecurity/privacy, change control, complaint handling, post-market monitoring, and applicable QMS/regulatory review.
5. **Commercial gate:** obtain dataset/model commercial rights, device/OEM data rights, regulatory classification/pathway by market, quality-system readiness, and legal review. A consumer disclaimer does not neutralize an intended diagnostic claim.

The FDA/IMDRF SaMD framework distinguishes valid clinical association, analytical validation, and clinical validation; these are separate evidence questions ([FDA/IMDRF SaMD Clinical Evaluation](https://www.fda.gov/files/medical%20devices/published/Software-as-a-Medical-Device-%28SAMD%29--Clinical-Evaluation---Guidance-for-Industry-and-Food-and-Drug-Administration-Staff.pdf)). Software that analyzes physiological signals can fall within regulated-device functions depending on intended use; confirm each claim and market with regulatory counsel ([FDA CDS decision step](https://www.fda.gov/medical-devices/digital-health-center-excellence/step-6-software-function-intended-provide-clinical-decision-support)). For US commercial device manufacturing, FDA QMSR took effect on February 2, 2026 and incorporates ISO 13485:2016 by reference ([FDA QMSR](https://www.fda.gov/medical-devices/postmarket-requirements-devices/quality-management-system-regulation-qmsr)).

## First delivery objective

Do not widen the consumer app with diagnoses. Deliver a **research-only dataset catalog + provenance/schema + offline benchmark harness** first, using a small license-cleared open dataset (initial candidate: Wrist PPG During Exercise) and synthetic/unit-test fixtures only for software plumbing. Report benchmark performance by participant/session split, signal-quality rejection, and failure class. No model output becomes a user physiological measurement until the Xiaomi channel mapping, sampling/timebase, physical units, and device-specific paired-reference validation are independently established.

## Initial benchmark run — 2026-09-28

- Added `research/clinical-data/registry.json`, pinned `wfdb` research-tooling requirements, and an offline benchmark under `research/clinical-data/`. Public waveform files are downloaded to ignored `.local-research-data/`, not bundled into either app. The local copy's 59 manifest-listed files verified against the publisher SHA-256 manifest.
- The runner parsed all 19 listed records and 218 30-second windows. It unwraps the documented modulo-60-second Shimmer time channel, resamples PPG to the nominal WFDB 256 Hz record grid, and keeps ECG annotated R-peak time on its own sample index. This nominal rate is not evidence of a shared physical clock. The source paper warns cross-device duration/alignment can differ by up to 1.21 seconds; all per-window metrics are descriptive under unverified relative-zero alignment, with no offset correction or confidence intervals.
- Synthetic/unit harness: **6 tests passed** (peak detector, spectral estimator, malformed samples, clock rollover/corruption, checksum match/mismatch/missing member). Dataset run: peak-count baseline MAE **38.18 bpm**, bias **+32.22 bpm**; spectral-peak baseline MAE **41.94 bpm**, bias **−6.17 bpm**. Both emitted a value for all reference-valid windows, but this emission coverage is not signal-quality or clinical coverage.
- Decision: these intentionally simple baselines fail as candidate product estimators and are retained only as reproducible negative controls. The later 0/218 exploratory candidate-rule acceptance is not evidence that all source signals are unusable; the rule combines detector/feasibility checks and the dataset has no manual quality labels. No tuning on this dataset, Xiaomi calibration, clinical claim, or app integration follows from this result. No independent holdout or population-level confidence interval is claimed.
- Evidence/source: [PhysioNet dataset and access terms](https://physionet.org/content/wrist/1.0.0/), [dataset paper describing the wrapped sample clock and alignment limits](https://www.mdpi.com/2306-5729/2/1/1), and [WFDB Python implementation/release](https://github.com/MIT-LCP/wfdb-python).

## Participant-level benchmark follow-up — 2026-09-28

- Benchmark v2 groups records by the dataset-local participant prefix and adds unweighted participant macro-MAE/bias beside pooled-window metrics. On 8 participants / 218 reference-valid windows, peak-count macro-MAE was **38.52 bpm** (pooled MAE 38.18); spectral macro-MAE was **44.93 bpm** (pooled MAE 41.94). Participant-level errors vary substantially, so pooled metrics alone conceal heterogeneity.
- Added a unit test proving macro averaging weights participants equally even with unequal window counts; benchmark harness now has **7 passing tests**. Dataset checksums remain 59/59 verified.
- This is not yet a participant-disjoint train/test evaluation because these are fixed, untuned deterministic baselines and no model fitting occurs. No valid signal-quality rejection rule exists yet; 100% estimate emission is not evidence of acceptable signals. Next gate is predeclared quality rejection/failure accounting and a split plan before evaluating any tuned model.

## Signal-screen and input-integrity audit — 2026-09-28

- Literature review: Orphanidou et al. developed a binary wearable ECG/PPG SQI tied to their own peak detector, 10-second windows, and manually labeled clinical cohorts. Their reported PPG template-correlation cutoff (0.86) was selected on their data with cross-validation; it is not a device-independent cutoff. The current benchmark uses a different Shimmer wrist dataset/detector, so the paper's feasibility/template criteria are implemented only as an explicitly exploratory transfer test, not a validated SQI or app gate ([paper DOI 10.1109/JBHI.2014.2338351](https://doi.org/10.1109/JBHI.2014.2338351); [full text](https://www.robots.ox.ac.uk/~davidc/pubs/jbhi_sqi2015.pdf)).
- Exploratory screen requires all three 10-second subwindows of a 30-second evaluation window to pass the paper-inspired feasibility checks and template-correlation threshold. On 218 reference-valid windows it accepted **0/218** (100% rejection); rejection reasons are non-exclusive: inter-pulse interval ratio 216, low template correlation 41, HR outside the screen 16. Since the dataset has no expert signal-quality annotations and PPG detector differs, sensitivity/specificity and post-screen MAE are **not estimable**. This is evidence against transferring this screen unchanged, not proof that every PPG segment is bad.
- Added synthetic tests for clean periodic, short, flat, nonfinite signals, and out-of-root record/checksum paths; total research harness is **11 passing tests**. Both baselines' unfiltered metrics remain poor (participant macro-MAE 38.52/44.93 bpm), so neither baseline nor this filter enters the product.
- Interpretation hazard: the inter-pulse-interval consistency rule can reject true irregular physiology as unsuitable for this HR estimator. It must never be presented as artifact proof, a rhythm label, or a reason to suppress a separate rhythm-review signal. This is an estimator-compatibility screen only.
- Input integrity bug found and fixed: dataset checksum entries are now constrained to remain inside the dataset root; RECORDS paths are similarly constrained; missing header/annotation files produce explicit `record_input_failures` instead of silent skips. Added path-traversal test. Actual dataset rerun verifies 59/59 checksums, processes 19/19 records, reports 218 windows and no record input failures.
